# src/tts/

**(내레이션 텍스트 + 스타일) ──▶ WAV**

내레이션 문장을 음성으로 만듭니다. `style`(GUIDE/CAUTION)에 따라 톤이 달라집니다.

## 파일

| 파일 | 역할 | 배포에 쓰임? |
|---|---|---|
| `finetune.py` | LoRA/PEFT 파인튜닝 | ✗ 학습 시에만 |
| `pregenerate.py` | 사전 생성 배치 — **기본 경로**. 등록 음식 전체의 음성 100개를 미리 만든다 | ✓ |
| `infer.py` | 추론 — 캐시에 없는 조합만 처리하는 **폴백**(라이브 생성) | ✓ |
| `worker.py` | `infer.py`를 별도 프로세스에서 실행하는 진입점 | ✓ |
| `perso_client.py` | Perso.ai API 호출 — 비교 평가용 | ✗ 평가 시에만 |

> 표의 "기본/폴백"은 **2026-08-21 Plan B 전환 결정** 이후 기준이다. 그전에는 `infer.py`의 라이브
> 생성이 기본이었고 사전 생성이 조건부였다 — 아래 절에 뒤집힌 경위가 있다.

## 기본 경로 vs Plan B — **Plan B로 전환 결정 (2026-08-21)**

원래 **기본**은 요청이 올 때마다 `infer.py`로 그 자리에서 음성을 만드는 라이브 생성이었고, TTFB(첫 소리가 나오기까지 걸리는 시간)가 목표를 넘으면 **Plan B**(사전 생성 캐싱)로 바꾸기로 되어 있었습니다.

**전환 기준과 실측 (2026-08-21, 원격 RTX 3080 Ti)**:

| 항목 | 값 |
|---|---|
| TTFB 목표 | 5~7초 |
| 라이브 생성 실측 — 콜드(모델 로딩 포함) | 61.3초 |
| 라이브 생성 실측 — 워밍업 후(상주 워커) | 약 33초 |

상주 워커 전환(PR #45)으로 요청당 90~160초 → 33초까지 줄였지만 목표(5~7초)에는 구조적으로 미달 → **Plan B 전환 결정.**

**Plan B 동작 방식**: `pregenerate.py`가 등록 음식 전체의 음성을 미리 생성하고, `src/pipeline.py`가 요청 시 이 캐시를 먼저 조회합니다(캐시 히트 시 1초 미만). 캐시에 없는 조합만 라이브 생성으로 폴백합니다.

만드는 파일은 **두 종류, 음식당 2개**입니다(2026-08-26 추가).

| 파일 | 내용 | 읽는 값 |
|---|---|---|
| `static/tts_cache/food_{id}_{STYLE}.wav` | 설명 전체(나레이션) | `narration` + 발음·알레르기 |
| `static/tts_cache/name_{id}.wav` | **음식 이름만** | `foods.name_kr` |

이름을 따로 두는 이유: 화면의 이름 옆 스피커를 눌렀을 때 설명까지 나오면 안 되는데, 통짜 wav에서 이름 부분만 떼어낼 방법이 없습니다. 이름 음성은 스타일을 `GUIDE`로 고정합니다 — 한 단어에 경고 톤을 씌울 이유가 없습니다.

두 음성 모두 **한글을 읽습니다**. 화면에는 로마자(`Galbitang`)가 보이지만 모델에는 한글을 넘깁니다 — 로마자를 주면 영어 음운으로 읽습니다.

이름은 한 단어라 나레이션보다 훨씬 짧게 걸립니다(실측: 50개 생성에 272초, 나레이션은 개당 20초).

```
# 배치 실행 (서비스와 같은 환경에서, 저장소 루트 기준 — 약 30분)
python -m src.tts.pregenerate            # 없는 조합만 생성 (이어하기 안전)
python -m src.tts.pregenerate --force    # 전부 다시 생성
```

배치는 각 항목의 생성 시간·음성 길이로 **RTF**(생성 시간 ÷ 음성 길이)도 같이 계산해 `eval/tts_pregen_log.csv`에 남깁니다.

## `infer.py` 실제 모델 연결 (2026-08-18)

`infer.py`가 실제 모델(Qwen3-TTS 1.7B Base + LoRA 어댑터 `k-bite-team/k-menu-qwen3-tts-lora`)을 호출하도록 연결됨. TTS 파트의 실제 학습 노트북에서 확인한 추론 코드(`generate_custom_voice` + 스피커 등록 방식)를 그대로 옮겨서 짰음 — 처음엔 다른 방식(`generate_voice_clone`)으로 추측해서 짰다가 노트북 확보 후 전면 재작성함. 자세한 경위는 `infer.py` 파일 상단 docstring과 `docs/specs/tts-finetuning.md`의 "구현 변경 이력" 참고.

**GPU 검증 완료 (2026-08-20)**: 원격 데스크톱(RTX 3080 Ti)에서 실제로 실행해 WAV 생성까지 확인됨. 당시에는 요청마다 별도 프로세스를 새로 띄워 모델을 처음부터 로딩해 **요청당 90~160초**가 걸렸다(GPU 성능 문제가 아니라 구조 문제라 장비 업그레이드로는 해결되지 않는다).

**그 뒤 두 번 바뀌었다**: ① 상주 워커 전환(PR #45)으로 요청당 33초까지 줄었고, ② 그래도 TTFB 목표(5~7초)에 구조적으로 못 미쳐 2026-08-21에 사전 생성 캐시를 기본 경로로 삼았다(위 절). 지금 라이브 생성은 캐시에 없는 조합만 타는 폴백이다.

## 왜 별도 프로세스(`worker.py`)로 실행하나

이 서비스는 같은 프로세스에서 PaddleOCR(paddle)도 로드한다. `paddleocr → paddlex → modelscope` 임포트 체인이 내부적으로 torch를 끌어오는데, paddle이 먼저 네이티브 DLL을 잡아둔 상태에서 torch를 로드하면 Windows에서 `shm.dll` 로딩이 깨진다(`OSError: [WinError 127]`).

그래서 `src/pipeline.py`는 TTS 추론을 `python -m src.tts.worker`라는 **완전히 별도인 자식 프로세스**에서 실행한다. 그 프로세스는 paddle을 전혀 임포트하지 않으므로 torch가 깨끗하게 로드된다. 텍스트·스타일을 stdin으로 넘기고 결과 JSON 한 줄을 stdout으로 받는 구조다.

## 음식명 발음 교정 — 한글 치환

영어 문장 안에 로마자로 적힌 음식명(`Tteokbokki`)은 모델이 **영어 음운으로 읽어버려** 발음이 부정확합니다. 그래서 TTS에 넘기는 문장에서만 음식명을 **한글 표기**(`떡볶이`)로 바꿉니다.

- **값**: 이미 있는 `foods.name_kr` — 표기 전용 컬럼을 따로 두지 않습니다. 등록된 50행이 전부 채워져 있어 음식이 늘어도 TTS 쪽에 추가 작업이 없습니다.
- **치환 위치**: `src/text_gen/narration.py`. 거기서 `foods` 행을 이미 조회하므로 `name_en`/`name_kr` 쌍이 손에 있습니다. 단어 경계로 매칭해서 짧은 이름이 긴 이름 안쪽을 파먹지 않게 합니다(`Galbi`가 `Tteokgalbi`를 건드리면 안 됨).
- **`infer.py`는 손대지 않습니다**: 받은 `tts_text`를 그대로 넘깁니다. 여기서 또 치환하면 이미 바뀐 이름을 두 번 처리합니다.
- **화면용 텍스트는 로마자 유지**: 여행자가 소리 내어 읽어야 하므로 `text`는 원본 표기 그대로입니다.
- **발음 안내 문장은 TTS 전용 행**: 화면용 `PRONUNCIATION`을 그대로 쓰면 `비빔밥 is pronounced "bee-bim-bap."`이 되어 같은 이름을 연달아 두 번 읽습니다. TTS 쪽은 `PRONUNCIATION_TTS` 카테고리를 씁니다.

앞서 쓰던 영문 리스펠링(`Tteokbokki` → `Duck-bok-kee`)은 폐기됐고 `RESPELL_MAP`·`apply_respelling()`도 코드에서 삭제했습니다. 전환 경위와 표기 21개 목록은 [`eval/TTS_MODULE.md`](../../eval/TTS_MODULE.md) 4절, 결정 기록은 [`docs/specs/tts-finetuning.md`](../../docs/specs/tts-finetuning.md) "구현 변경 이력 (2026-08-25, 최종)" 참고.

검증은 MOS 같은 정량 채점이 아니라 몇 개를 직접 들어보고 사람이 판단하는 방식이며, **한글 표기는 아직 청취 확인 전입니다**.

우리 파인튜닝 모델이 상용 서비스 대비 어느 정도인지 재기 위한 **비교군**입니다. 같은 내레이션 텍스트를 양쪽에 넣고 MOS로 채점합니다. 결과는 `eval/`에 기록합니다.
