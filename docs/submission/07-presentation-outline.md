> 제출물 7번 — 발표자료(PPT)의 슬라이드별 원고
>
> **⚠️ PPTX 파일은 아직 만들지 않았다.** 지급된 발표자료 양식의 필수 목차에 맞춰야 하는데

## 발표의 한 줄 축

> "메뉴판을 못 읽는 관광객에게 **번역이 아니라 '이 음식이 무엇인가'를** 텍스트와 음성으로 준다.
> 그 과정에서 **측정하고, 범위를 좁히고, 구조를 바꿨다.**"

## 슬라이드 2 — 한 문장 문제 정의

> **한국 음식에 익숙하지 않은 영어권 개별 관광객은, 글자만 옮기는 기존 번역 앱 방식으로는
> 음식의 맛·재료·맵기·먹는 법을 알 수 없어 아는 메뉴만 고르거나 주문을 포기하게 되므로,
> 메뉴판 사진 한 장으로 음식 정보를 영어 텍스트와 음성으로 안내하는 서비스가 필요하다.**

화면 중앙에 실제 사례 하나만 크게:

```
곱창전골  →  Beef intestine hot pot
```
*번역은 됐다. 그런데 이게 무슨 음식인지는 여전히 모른다.*

**발표 노트**: 평가에서 가장 먼저 묻는 질문이 "누가, 무엇 때문에, 얼마나 절실한가"다.
이 슬라이드 하나로 답한다. 기술 이야기는 아직 꺼내지 않는다.

## 슬라이드 9 — 그래서 무엇을 뺐는가 ★

> 이 슬라이드가 발표의 핵심이다. 가이드가 "주니어와 시니어를 가르는 지점"으로 지목한 항목이다.

| 뺀 것 | 왜 | 대신 무엇을 했나 |
|---|---|---|
| **실시간 TTS 생성** | RTF 1.47 — 하드웨어로 못 넘는 벽 | 등록 음식 50개를 **사전 생성해 캐시**. 33초 → **1.8ms** |
| **음성 질문 입력(STT)** | 14일·4명(중 1명 이탈) 안에서 OCR·TTS 파인튜닝을 둘 다 하려면 입력 경로를 하나로 고정해야 했다. 우리 시나리오는 "말을 거는" 것이 아니라 **"메뉴판 앞에서 사진을 찍는"** 것이다 | 입력을 **사진 한 장**으로 좁히고, 그 대신 출력 음성의 품질·발음·톤에 자원을 몰았다 |
| **설명 생성용 LLM** | 알레르기·재료에서 **환각이 나오면 안전 문제** | 팀이 작성해 DB에 넣은 문장만 조회·조합 |
| **미등록 음식 추측** | 틀린 음식 설명은 안 하느니만 못하다 | `unsupported_food`로 정직하게 안내 |
| 다국어·주문결제·실시간 통역 | 범위 폭발 | MVP 이후 과제로 명시 |

**발표 노트 (STT 질문이 나올 것에 대비)**:
"가이드 요건에 STT가 있는데 왜 없느냐"는 질문은 반드시 나온다. 방어하지 말고 먼저 말한다 —
**"저희는 STT를 넣지 않기로 결정했고, 그 이유는 시나리오와 자원 배분입니다"**. 그리고 대신
무엇에 그 자원을 썼는지(TTS 9차까지의 하이퍼파라미터 탐색, 발음 문제 해결, 캐시 전환)를 보여준다.
가산이 아니라 **감점 요인임을 알고 내린 판단**이라고 분명히 말하는 편이 얼버무리는 것보다 낫다.

## 슬라이드 11 — 딥러닝 활용의 깊이 ② 발음 문제 (재학습 없이 해결)

| 시도 | 결과 |
|---|---|
| IPA 발음기호 입력 | 모델이 기호를 글자로 읽음 → 폐기 |
| 한글 **병기** (`떡볶이 (tteokbokki)`) | 부자연스러움 → 폐기 |
| 영문 리스펠링 (`Tteokbokki` → `Duck-bok-kee`) 21개 수작업 | 21개는 개선됐지만 **나머지 29개까지 부정확** → 폐기 |
| **TTS 입력에서만 음식명을 한글로 치환** | ✅ **50개 전부 한 번에 해결** |

**핵심**: 원인이 **철자가 아니라 모델이 읽는 음운 체계**였다. 로마자로 적혀 있는 한 모델은
영어 음운으로 읽는다. 한글로 적으면 베이스 모델의 한국어 능력이 작동한다.
**구현은 정규식 치환 한 줄. 재학습도 사전 테이블도 필요 없었다.**

화면에는 로마자를 그대로 남긴다 — 여행자가 소리 내어 읽어야 하는 정보이기 때문이다.

**각주**: `eval/TTS_MODULE.md` 4절 · `src/text_gen/narration.py :: _to_tts_text()`

## 슬라이드 12 — 딥러닝 활용의 깊이 ③ OCR 파인튜닝의 대가

**넣을 그림**: [가격 숫자 인식 비교](assets/chart-ocr-digits.png)

| 인식기 | 숫자 완전일치 |
|---|---|
| base | 77.78% |
| 파인튜닝 단독 | **5.56%** ← 잃었다 |
| production (배포 경로) | **77.78%** ← 되찾았다 |

- **원인**: catastrophic forgetting — 음식 50개 글자만 모은 커스텀 딕셔너리로 학습해
  숫자·통화기호를 읽는 능력을 잃었다 (`9,000` → `C0`)
- **대응**: 모델을 되돌리지 않고, **한글이 없는 조각은 base 결과를 채택**하는 하이브리드
- **결과**: 파인튜닝의 손실이 사용자에게 도달하지 않는다

**발표 노트**: 실패를 숨기지 않는 것이 오히려 강점이다. "파인튜닝이 이긴 항목만 보여주는 팀"과
"진 항목과 그 대응까지 보여주는 팀"의 차이를 만든다.

## 슬라이드 13 — 모델 비교 실험 결과

[08. 모델 비교 실험](08-model-experiments.md)의 핵심 표 두 개 + 그래프.

**넣을 그림**: [OCR 난이도별 성능](assets/chart-ocr-categories.png) · [Perso.ai 대비 UTMOS](assets/chart-tts-perso.png)

| 항목 | 값 |
|---|---|
| OCR 음식명 매칭 재현율 | **91.67%** (목표 90%) |
| 라벨 완전일치 | 66.67% — **25%p 차이를 매칭이 메운다** |
| TTS Val Loss | 10.87 → **8.8919** (−18%) |
| Perso.ai 대비 UTMOS | GUIDE 104.3% · CAUTION 106.9% |

**반드시 함께 말할 것 (정직성)**:
- 사람 MOS는 **아직 한 건도 없다(0/5명)**. 평가 자료는 준비됐고 채점이 남았다
- UTMOS는 **3차 체크포인트·구 설정 기준**이라 현행 배포와 조건이 다르다
- Perso.ai 비교는 **n=1**이라 통계적 유의성이 없다
- base OCR 기준선은 테스트셋이 로컬에만 있어 **미측정**이다

## PPTX를 만들 때 지킬 것

1. **한 장에 메시지 하나.** 본문은 문장이 아니라 구절로.
2. **수치 슬라이드에는 출처를 각주로.** (예: `eval/model_comparison.md` 3절)
3. **슬라이드 9는 빼지 않는다.** 가이드가 명시적으로 평가에 반영한다고 적은 항목이다.
4. 그림 파일은 [`assets/`](assets/)에 전부 있다 — 차트 5개, 캡처 5개, 합성 메뉴판 1개.
5. 오디오는 [`assets/audio/`](assets/audio/)에 있다. 발표장에서 바로 재생할 수 있게 슬라이드에 삽입한다.
