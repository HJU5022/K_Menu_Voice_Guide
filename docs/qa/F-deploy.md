## 배경 — 이 영역만 보는 것

A~E는 "기능이 맞게 동작하는가"를 본다. **이 영역은 "이상한 입력과 나쁜 상황에서 버티는가"를 본다.**
시연 도중 서버가 죽는 사고는 대부분 여기서 미리 잡을 수 있었던 것들이다.

방어 코드는 이미 들어가 있다. 확인할 것은 **그게 실제로 작동하는지**다.

| 상황 | 설계된 응답 |
|---|---|
| 이미지가 아닌 파일 | **400** |
| 10MB 초과 | **413** |
| 빈 파일 | **400** |
| 확장자만 이미지고 열리지 않는 파일 | **400** |
| 서버 내부 오류 | 500 |

400·413과 500을 구별하는 이유: 500은 "서버 잘못"이라는 뜻이라, 화면이
**사용자가 이상한 파일을 올린 것**과 **서버가 죽은 것**을 구별하지 못한다.
둘은 사용자가 할 행동이 정반대다 — 앞은 다른 사진을 고르면 되고, 뒤는 기다려야 한다.
**그래서 잘못된 입력에 500이 나오면 그 자체가 결함이다.**

## 실행 명령어


**테스트용 잘못된 파일 만들기:**

```bash
cd /tmp
printf 'not an image' > bad.txt                      # 이미지 아님
: > empty.jpg                                        # 빈 파일
printf 'not an image' > fake.jpg                     # 확장자만 jpg
dd if=/dev/urandom of=big.jpg bs=1m count=12 2>/dev/null   # 12MB
ls -la bad.txt empty.jpg fake.jpg big.jpg
```

**각각 올려보기 (응답 코드만 확인):**

```bash
for f in bad.txt empty.jpg fake.jpg big.jpg; do printf "%-12s " "$f"; curl -s -o /dev/null -w "[HTTP %{http_code}] %{time_total}s\n" -X POST https://hju5022-k-menu.hf.space/api/analyze -F "image=@/tmp/$f"; done
```

**연속 요청 10회 (안정성):**

```bash
cd /Users/jeong-un/Documents/Projects/Main_1_projects && for i in $(seq 1 10); do printf "%2d " $i; curl -s -o /dev/null -w "[HTTP %{http_code}] %{time_total}s\n" -X POST https://hju5022-k-menu.hf.space/api/analyze -F "image=@demo_menus/01_수식어_시연.jpg"; done
```

**동시 접속 3개 (시연 중 여러 명이 동시에 쓰는 상황):**

```bash
cd /Users/jeong-un/Documents/Projects/Main_1_projects && for i in 1 2 3; do (curl -s -o /dev/null -w "동시$i [HTTP %{http_code}] %{time_total}s\n" -X POST https://hju5022-k-menu.hf.space/api/analyze -F "image=@demo_menus/01_수식어_시연.jpg") & done; wait
```

### 특히 노려볼 것

- **큰 파일이 언제 끊기는가** — 전량을 다 받은 뒤에 실패하면 그동안 서버 자원을 잡아먹는다.
  기록에 따르면 예전에 12MB가 3.3초에 걸쳐 전부 수신된 뒤에야 실패했고, 지금은 조각조각
  읽으면서 넘는 순간 끊도록 고쳐져 있다. **실제로 빨리 끊기는지 F-05에서 확인한다.**
- **임시 파일이 쌓이는가** — 요청마다 서버 디스크에 파일이 남으면 시연 중에 디스크가 찬다.
  F-07·F-10을 돌린 뒤에도 응답 시간이 그대로인지 본다
- **콜드스타트 시간** — 시연 직전에 미리 한 번 요청해서 깨워둬야 하는지 판단하는 근거가 된다
