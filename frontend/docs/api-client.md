# API Client Rules

## Why

프론트가 특정 개발 PC 주소에 묶이지 않고, 개발·검증·배포 환경에서 같은 방식으로 API를 호출해야 한다.

## Goal

API 기본 주소는 `VITE_API_BASE_URL`로만 관리하고, 응답을 화면 상태에 일관되게 연결한다.

## What

| 사용자 행동 | 프론트 입력 | 화면에 필요한 결과 |
|---|---|---|
| 메뉴 사진 분석 | 이미지 파일 | 상태, OCR 원문, 음식 후보(위치·가격·썸네일 포함) |
| 음식 후보 선택 | 음식 ID | 6개 상세 항목, 나레이션 문장, **두 가지 오디오 URL**(이름·설명)과 각각의 상태 |
| 지원 음식 확인 | 없음 | 안내 가능한 음식 전체 목록 (설정 창) |
| 장바구니 담기·빼기·비우기 | 메뉴 줄 정보 + 증감 | **카트 전체 상태** — 부분 갱신을 조합하지 않는다 |
| 오디오 재시도 | 선택 음식 정보 | 새 오디오 상태·재생 URL |
| 잘못된 파일 업로드 | 이미지가 아닌 파일·10MB 초과·빈 파일 | 400·413과 사유. 사진을 다시 찍으라고 하지 않는다 |

## How

```text
VITE_API_BASE_URL (+ ?api= 오버라이드)
→ axios 인스턴스 (baseURL · 타임아웃 90초)
→ 응답을 TypeScript 화면 모델로 변환
→ 로딩 / 성공 / 오류 화면 전환
```

HTTP를 아는 모듈은 `client/src/lib/api.ts` **하나뿐이다.** 화면은 axios를 몰라도 되게, 이 모듈이
오류 종류까지 정해서 던진다.

- 소스 코드에 개인 PC 주소를 고정하지 않는다.
- `VITE_` 변수에는 공개 가능한 값만 둔다.
- **주소 오버라이드**: 주소창의 `?api=https://...`를 localStorage에 기억해 기본 주소 대신 쓴다.
  시연 중 서버를 갈아탈 때 재배포 없이 옮기기 위한 장치이며, 기본값이 아니면 화면이 알린다
  (`isUsingCustomApi`).
- **타임아웃 90초**: 상한이 없으면 서버가 응답하지 않을 때 화면이 영원히 "처리 중"으로 돈다.
  GPU Space는 잠들었다 깨는 데 오래 걸리므로 콜드 스타트는 정상으로 보되 그보다 훨씬 못 미치는
  지점에서 끊는다.
- **400·413은 `BadUploadError`로 갈라 던진다.** 서버 장애와 사용자가 할 행동이 정반대다 —
  이쪽은 다른 사진을 골라야 하고, 저쪽은 기다렸다 다시 시도해야 한다.
- **장바구니 요청에는 `X-Cart-Id` 헤더가 필수다.** 로그인이 없어 브라우저가 UUID를 만들어
  localStorage에 두고, 서버는 모르는 ID를 빈 카트로 취급한다(`docs/specs/cart.md`).
- **오디오 경로는 상대 경로다.** `resolveAudioUrl()`이 API 주소를 앞에 붙여야 재생된다.
- **목록 응답은 배열인지 확인하고 쓴다.** API 주소가 비어 있으면 요청이 같은 출처로 가고, 정적
  파일 서버가 `index.html`을 200으로 돌려줘 axios가 성공으로 본다 — 그대로 `.map`을 부르면 앱
  전체가 흰 화면이 된다.
- 요청 전에는 로딩 상태를 보이고, 실패하면 기술 오류 대신 사용자용 오류 화면을 보인다.

## AC (Given-When-Then)

- GIVEN: 배포 환경 API 주소가 설정됐다. WHEN: 사용자가 메뉴를 분석한다. THEN: 코드 수정 없이 해당 주소로 요청한다.
- GIVEN: 요청이 실패했다. WHEN: 프론트가 실패를 감지한다. THEN: 재시도 가능한 오류 화면을 표시한다.
