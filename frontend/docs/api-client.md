# API Client Rules

## Why

프론트가 특정 개발 PC 주소에 묶이지 않고, 개발·검증·배포 환경에서 같은 방식으로 API를 호출해야 한다.

## Goal

API 기본 주소는 `VITE_API_BASE_URL`로만 관리하고, 응답을 화면 상태에 일관되게 연결한다.

## What

| 사용자 행동 | 프론트 입력 | 화면에 필요한 결과 |
|---|---|---|
| 메뉴 사진 분석 | 이미지 파일 | 상태, OCR 원문, 음식 후보 |
| 음식 후보 선택 | 음식 ID | 6개 상세 항목, 나레이션 문장, **두 가지 오디오 URL**(이름·설명)과 각각의 상태 |
| 오디오 재시도 | 선택 음식 정보 | 새 오디오 상태·재생 URL |
| 잘못된 파일 업로드 | 이미지가 아닌 파일·10MB 초과·빈 파일 | 400·413과 사유. 사진을 다시 찍으라고 하지 않는다 |

## How

```text
VITE_API_BASE_URL
→ fetch 요청
→ 응답을 TypeScript 화면 모델로 변환
→ 로딩 / 성공 / 오류 화면 전환
```

- 소스 코드에 개인 PC 주소를 고정하지 않는다.
- `VITE_` 변수에는 공개 가능한 값만 둔다.
- 요청 전에는 로딩 상태를 보이고, 실패하면 기술 오류 대신 사용자용 오류 화면을 보인다.

## AC (Given-When-Then)

- GIVEN: 배포 환경 API 주소가 설정됐다. WHEN: 사용자가 메뉴를 분석한다. THEN: 코드 수정 없이 해당 주소로 요청한다.
- GIVEN: 요청이 실패했다. WHEN: 프론트가 실패를 감지한다. THEN: 재시도 가능한 오류 화면을 표시한다.
